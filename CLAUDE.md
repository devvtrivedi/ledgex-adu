Every CHECK constraint in a new migration must be given an explicit `CONSTRAINT <name>` — never let Postgres invent one (`rule_check1` and friends already exist from older migrations; they are not being renamed, but nothing new should add to that list). An auto-generated name can't be targeted by a later migration without first querying `pg_constraint`, which 0015 had to do.

Ingest code refreshing `current_fact`: read `db/README.md` first. **Corrected (D11, P59):** the previous line here overgeneralized — db/README.md's own verified test shows `CONCURRENTLY` works on the very first refresh when the database was bootstrapped by replaying `db/migrations/*.sql` in order (`make schema`, or any environment applying migrations directly), because `CREATE MATERIALIZED VIEW` populates the view immediately even with zero matching rows. It only fails first-time on a database bootstrapped by restoring `db/schema.sql` (a `pg_dump --schema-only` dump, which always emits `WITH NO DATA` for a materialized view) — Postgres categorically refuses `CONCURRENTLY` against an unpopulated view there. The error was in the safe direction (over-cautious, not under), so ingest code should still do a plain refresh first as its own general rule regardless of bootstrap path — but do not assume the failure itself is universal when reasoning about a specific database's state.

CI (`db.yml`) always applies every migration to an empty database first — `make schema` itself never runs `db/seeds/`, in CI or locally, in any job. A migration that corrects already-seeded data must therefore also work standalone against a migrations-only database, not just a seeded one — verify both:
- `UPDATE ... WHERE ...` no-ops harmlessly on absent rows (0023, 0026, 0030).
- A plain `INSERT` naming a specific seeded id raises `foreign_key_violation` on a missing parent row — it does NOT no-op. Use `INSERT ... SELECT ... WHERE id IN (...)` (or an equivalent existence guard) instead (0032).

Whether a CI database *stays* migrations-only for the rest of that job's run depends on which job — this is where an earlier version of this paragraph went wrong (see the correction below), so check the job, don't assume. `db.yml`'s `schema` job runs `db/seeds/day4_sources.sql` against its own main database between `make db-test` and `make golden` — added by P36 (finding #38) specifically so `day4_sources.sql` and `scripts/check_golden.py`'s own independent reference-row seed cannot silently disagree with nothing in CI to catch it. So `make golden`, `make conformance`, `make viewer-test` and `make test`, as CI actually runs them in that same job, see seeded state on every push. The `p5-acceptance` job's own separate `ledgex_ci_p5` database and the `phaseb-acceptance` job's own database are the ones that stay migrations-only for their entire run — their own step comments say so explicitly, and that part was always true. **Corrected (D11, P59):** this paragraph previously attributed `ledgex_ci_p5` to the `schema` job; it is `p5-acceptance`'s own, separate job (confirmed against db.yml's own job names, not assumed) — an easy mistake given both databases share the `ledgex_ci` prefix, but they are three distinct jobs (`schema`, `p5-acceptance`, `phaseb-acceptance`) with three distinct databases (`ledgex_ci`, `ledgex_ci_p5`, and `phaseb-acceptance`'s own).

**Corrected 2026-08-22 (P53, answering P52's own §9 question 3):** this paragraph previously claimed, as a blanket statement, that CI "never runs `db/seeds/`" across every job. That stopped being true at P36 and the claim was never updated — a stale instance of exactly the failure class this file exists to prevent. The discipline above (verify a migration against a migrations-only database) is unaffected and remains correct; only the blanket "never seeded, anywhere" claim was wrong.

Companion rule, from 0026: a guarded migration alone is a permanent no-op on every future fresh install, because migrations apply before any seed runs — a seed file that was never corrected at the source just re-inserts the wrong data right after the guarded migration's WHERE clause matches nothing. A data correction needs both halves, every time: the guarded migration (for a database already seeded before the fix) and the fix at the seed source (for every install after it).

A fix at the source prevents recurrence — it does not clean up a database that already has the bad data sitting in it. `ledgex_schema_check` (the local dev database, matching the Makefile's own `DATABASE_URL` default) carried `cc0`/`cc_by_4_0` licence rows with `cleared_by='test'` and a fabricated `observed_at`, created by an old, unnamespaced version of `db/tests/invariants.sql` before it was fixed to use `test.*` ids. Every such fix needs a paired question: what about databases already affected? Usually the answer is a guarded migration (see above). But once a table is immutable (`licence` since 0027, `licence_channel` since 0033), a migration can no longer touch the bad row at all — the only remaining answer is to rebuild: drop the database, reapply every migration, reseed. Confirm this by querying the specific columns the contamination affected before dropping anything, so the before-state is on record rather than inferred.
